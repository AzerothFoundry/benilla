# Realm Companion 性能优化方案

状态：规划，尚未实施性能行为变更。基线为 `companion-v0.4.5`（build 13）。

## 基线与已知证据

当前发布版待机时，单次 `ps` 回读 CPU 72.3%，用户观察约50%–80%。macOS 的100%约为一个逻辑核心；这不是整机CPU占用。此单点不是平均值、P95或稳定性能承诺。

已做3秒原生采样，包含ECS调度和Metal资源操作；等待栈不代表CPU消耗，暂不能给各系统分配占比。确认的代码事实：

- 未覆盖 `WinitSettings`，继承game模式：聚焦Continuous，非聚焦为60Hz超时的reactive_low_power。实际FPS尚需计数，不能直接称为60FPS实测。
- 身体点击遮罩最高30Hz重绘并GPU读回；并非每个主循环都读回，但待机也会刷新。
- 相机与投影每帧重设，动作解析复制JSON并检查事件；是否为主要瓶颈需测量。
- 复用WorldPlugins及相关初始化，尚未按桌宠裁剪；模块存在不等于正在加载整个世界或占用主要CPU。
- 设置UI关闭后相关相机停用，但主循环、待机骨骼等仍更新。

版本内容分为渲染引擎、桌宠应用、文档三个提交。它是客户端消费端的版本基线；当前Agent运行版本的源码尚有独立未提交改动，不包含在本标签中。游戏MPQ和运行配置也不进Git。源码可构建不等于安装包逐字节可重现。

## 目标与不可退化的行为

保留自然待机、移动/坐骑/施法、单次表情及Agent抢占、中文气泡/声音、透明背景、身体命中与透明区域穿透、多实例、设置实时预览。

第一阶段以同场景CPU均值降低至少40%为验收目标，而不是预先保证某个绝对百分比；达不到就根据新采样继续定位。若初始稳定CPU约70%，目标约42%或更低。后续再评估能否低于20%，不能在未测量前承诺。

持续移动/跳舞目标30FPS；待机初始15FPS；睡眠/离线初始5FPS。它们是待验证的初始档位，不是已上线配置。离线睡眠仍有呼吸动作，不能直接冻结成单帧。选择/设置打开、拖动和缩放期间维持30FPS。

Agent可见动作更新到呈现、身体点击重新可用的延迟目标P95低于100ms；使用客户端接收时间开始计时，网络延迟另记。若低帧率造成输入/动作不达标，应增加事件唤醒，不用夸大降耗结果换响应。

## 实施顺序与提交边界

| 阶段 | 独立改动 | 验证与回退 |
|---|---|---|
| P0 测量 | 增加可关闭的低频性能计数：帧数、更新/渲染耗时、遮罩捕获/读回次数、模型重建、相机变更、SSE状态更新；收集系统CPU/内存 | 日志不含账号口令或逐帧海量JSON。观察器本身开关A/B，确认成本可忽略。提交只含观测与测量工具 |
| P1 刷新策略 | 仅桌宠配置动态刷新档位；所有窗口焦点变化不得恢复游戏式无界Continuous；新SSE状态、鼠标、菜单、设置触发及时更新 | 15/30/5FPS与0.4.5同场景比较。核对动画时间与真实时间一致，避免把播放速度也减半；失败可单独回退此提交 |
| P2 命中遮罩 | 待机初始5Hz、动作15Hz、鼠标接近/拖动时最高30Hz；按可见姿势/外观/尺寸/投影变化更新；隐藏窗口停止捕获 | 合法缓存按几何版本管理，不能只延长旧0.5秒TTL而让失效遮罩长期点击。GPU读回保持单个在途；尺寸/角色变化立即作废。再测蓝框、alpha和命中IoU |
| P3 重复工作 | 相机/投影/Transform只在值改变时写入；按session+sequence解析新增事件；DBC查询结果/动画优先级缓存；减少每帧JSON克隆 | 保留SSE重连、换角色、动作结束、取消及离线状态。正常待机不重复重建模型。计数与CPU采样共同证明收益 |
| P4 引擎裁剪 | 建立companion专用插件集合，按资源/系统依赖逐项剔除地形流送、世界天气/水体/地图等不需要模块；单独评估较小任务池 | 先画实际依赖表，逐项关停，不直接删WorldPlugins。保留模型骨骼、材质、光照、粒子/ribbon等确实需要的模块。正常游戏客户端路径保持不变 |
| P5 发布 | 独立性能版本，保留0.4.5基线和安装包备份，更新文档、版本号和部署回执 | 校验源码提交、安装二进制哈希、签名、启动与退出；有回归直接恢复旧包，不修改服务端 |

每阶段独立Conventional Commit，完成并验证后再推进下一阶段。不要同时降低帧率、关闭特效、移除插件然后把全部收益归给某一项。单线程与多线程调度作为测量选项，不能未经对照直接认为减少线程必然更快。

## 可重复的测量方法

1. 固定同一机器、电源模式、显示器刷新率、窗口尺寸/比例、角色与装备、特效开关；只运行一个被测桌宠实例。记录其它游戏客户端/构建负载，避免编译期间CPU数据充当运行基准。
2. 启动后预热30秒；每场景采集60秒，每秒系统CPU读数；重复三轮。用进程CPU时间差/墙钟作均值，另报每秒样本中位数、P95；内存区分RSS与包含GPU/共享内存的physical footprint，不混称。
3. CPU高的场景再取原生采样，区分运行/阻塞；分别观察主循环、渲染提交、任务池唤醒、GPU读回及资源创建。实际FPS、GPU时间有工具证据才报告，否则标未知。
4. A/B至少含基线、P1、P1+P2；若差异低于环境波动，先重复或延长测量，不认定优化有效。

| 场景 | 核对内容 |
|---|---|
| 在线待机，设置关闭 | CPU、帧率、呼吸与装备效果、SSE不变时主循环 |
| 跑步/坐骑/跳舞 | 30FPS是否平滑；单次动作结束后恢复；骨骼/读回成本 |
| 表情中Agent动作切换 | 中断延迟；气泡和声音及时退出；无陈旧事件重播 |
| 离线睡眠/重连 | 5FPS是否可接受；唤醒延迟；保留外观与断线恢复 |
| 角色选择/设置 | 八行列表、缩放/外观实时预览、滚轮和输入、关闭后恢复 |
| 透明区域/身体/拖动 | 透明区与气泡穿透、身体双击、按下后拖出身体仍能完成拖动 |
| 高缩放/换装/换角色 | 遮罩立即失效并重建；无蓝框/残留；多实例不串配置 |

## 本轮范围

本轮只提交0.4.5版本并形成方案，不改刷新行为，不发布性能优化版本，不重启游戏服务器。优化将从P0测量开始，避免只凭主观流畅或CPU瞬时读数宣布完成。
